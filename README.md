## 1. 产品定位

### 目标用户

第一批面向活动执行公司和企业市场部门，以企业年会、品牌发布会为首批验证场景。婚礼、商场促销和展会作为后续主题扩展。

### 核心价值

1. 熟悉玩法：竞速、赛马、拔河等玩法容易解释，降低现场参与门槛。
2. 人的代入：部门、阵营、昵称和个人贡献进入游戏。
3. 品牌代入：Logo、配色、产品素材、活动目标形成统一表达。
4. 快速搭建：自然语言生成活动配置、主持词、主题素材和成绩卡。
5. 可控执行：主持人能预览、开始、暂停、结束和处理异常。

示例需求：

> 给销售年会做一场两分钟的团队赛马，华东、华南、华北三个大区参赛，红金风格，主题是冲刺年度目标。

系统生成队伍、规则、视觉主题、主持词和预览。负责人确认发布后，参与者扫码加入活动，游戏结束生成团队成绩和个人贡献卡。

### 产品边界

AI 基于已经实现和验证的机制生成配置。首期不生成任意可执行游戏代码，也不承诺无限玩法。剧情是可选的活动包装，不要求每场活动都有复杂故事。

“几分钟生成”是需要实测的产品目标。先提供内置素材的完整预览，生成素材完成后再替换；正式发布必须确保资源齐全。

## 2. MVP 范围

| 环节 | 首期内容 | 说明 |
| --- | --- | --- |
| 活动创建 | 一句话需求、Logo 上传、品牌色、人数与时长 | 未提供的信息使用可见默认值 |
| 活动预览 | 主题、队伍、规则、主持词、模拟运行 | 用户无需编辑 JSON |
| 入场 | 微信身份登录、房间加入、临时昵称头像 | 不默认获取微信头像昵称，不强制手机号 |
| 签到 | 参与人数、简洁玩家列表或上墙 | 复杂 3D 签到后置 |
| 个人/团队竞速 | 点击推动进度，赛马为首个主题 | 先点击，摇动作为后续可选输入 |
| 团队拔河 | 阵营贡献推动目标 | 复用房间、计数、阶段、结算 |
| 主持人控制 | 开始、暂停、继续、结束、状态提示 | 服务端校验权限与阶段 |
| 结算 | 团队排行、个人贡献、品牌成绩卡 | 结果先持久化，再生成素材 |

### 首期不包含

- 红包支付、复杂抽奖、会员积分、优惠券核销。
- 接金币、飞机大战、跑酷等需要额外操作与碰撞规则的游戏。
- 任意代码生成、自由游戏编辑器、自动生成复杂角色动画。
- AI 随意修改奖品、竞赛分数或比赛时长。
- Kafka、跨区域部署、复杂微服务拆分。
- H5 玩家端：首期玩家必须使用微信身份，优先小程序。

## 3. 用户流程

### 活动负责人

输入需求 → 上传品牌素材 → 生成草稿 → 查看模拟预览 → 修改文案与配置 → 校验发布 → 打开大屏与主持人控制台 → 运行活动 → 查看战报。

### 参与者

微信扫码 → 小程序登录 → 加入对应房间 → 设置临时展示身份/分配阵营 → 等待开始 → 点击互动 → 查看成绩卡。

### 主持人

确认资源加载和在线人数 → 开始 → 观察参与与连接状态 → 必要时暂停或结束 → 确认结算。

微信登录、二维码参数和发布要求应在开发时依据微信官方文档核实。AppSecret 和会话敏感信息只保存在服务端；玩家身份不能代替房间访问权限。

## 4. 技术架构

### 技术选择

| 层 | 计划技术 | 职责 |
| --- | --- | --- |
| 管理端 | Next.js + TypeScript + shadcn/ui + Tailwind CSS | 创建、配置、预览、控制与报告 |
| 大屏端 | TypeScript + PixiJS，React 管理页面外壳 | 场景、精灵、动画、粒子、排行 |
| 玩家端 | 原生微信小程序 + TypeScript | 登录、入场、操作与个人反馈 |
| 后端 | Python + FastAPI | API、身份、活动、WebSocket、房间运行 |
| 数据库 | PostgreSQL | 活动、版本、成员关系、成绩、任务 |
| 缓存 | Redis | 会话、房间归属、快照、任务协作 |
| 后台处理 | 独立 Python Worker | 模型调用、素材处理、战报生成 |
| 资源 | 对象存储 + CDN | Logo、主题素材、音效、成绩卡 |

具体依赖版本在编码阶段核实并锁定。PixiJS 负责渲染，玩法判定由后端执行；美术品质取决于素材与动画制作，不由引擎自动提供。

### 管理端框架与 UI 决策

- 管理端及主持人控制台使用 Next.js App Router + TypeScript + shadcn/ui + Tailwind CSS。
- shadcn/ui 提供可放入项目并定制的 UI 组件，不是独立应用框架；需要与 React 及构建工具配合。
- 已按用户选择采用 Kiranism 的 Next.js 模板，保留其 shadcn/ui 风格和 TanStack Form。业务身份校验、游戏运行与计分仍计划由 Python/FastAPI 服务负责。
- UI 采用统一的颜色、间距、字体、圆角与状态规范，围绕活动创建和预览设计；shadcn/ui 用于表单、弹窗、导航等界面，大屏游戏画面继续由 PixiJS 渲染。
- 开发时补齐路由、API 状态管理、表单校验、加载与错误状态、键盘操作和移动端适配，不把组件安装视为界面完成。
- 官方接入参考：[Vite](https://ui.shadcn.com/docs/installation/vite)、[Next.js](https://ui.shadcn.com/docs/installation/next)。

### 运行结构

```text
活动管理端 / 主持人控制台     微信小程序       大屏播放器
             \                  |                /
                      HTTPS / WSS
                           |
                   FastAPI 实时服务
             身份 / 活动 / 发布 / 房间 / 结算
                     |             |
                PostgreSQL       Redis
                     |
               后台任务 Worker
             AI 编排 / 素材 / 战报
                     |
                对象存储 / CDN
```

首期采用模块化单体、单代码仓库；实时服务和后台任务独立进程运行。AI 调用或图片处理不能阻塞游戏循环。已发布活动应在 AI 服务不可用时仍能运行。

## 5. 后端模块

1. 身份与权限：组织、活动负责人、主持人、玩家、短期会话和房间访问。
   管理端支持邮箱注册、登录、邮箱验证和密码恢复；玩家端保留微信登录。新注册用户仅拥有自己的工作区权限。
2. 活动管理：草稿、模板选择、品牌素材、发布版本。
3. AI 生成：需求解析、机制选择、文案、配置、资源任务与校验。
4. 资源管理：上传、资源标识、加载清单、版本和存储。
5. 房间运行：成员、阵营、输入、计时、阶段、状态同步和重连。
6. 玩法机制：竞速、拔河；后续扩展答题与投票。
7. 主持人控制：有权限、可去重的控制指令及操作记录。
8. 结算与战报：幂等结算、排行、贡献卡、汇总指标。

## 6. 游戏运行设计

### 权威状态

每个房间同一时刻由一个运行实例负责。玩家上报操作，服务端校验并计算成绩。大屏根据服务端状态平滑播放动画。

首期单个实时进程持有活跃房间。不能直接增加多个 Web 服务进程后假设房间内存共享。后续扩容需要明确房间归属、连接路由、实例失效处理与恢复策略。

### 输入与同步

- 点击输入可按 100～200ms 窗口合并，作为压测初始参数。
- 服务端可从约每秒 10 次的大屏状态更新起步，按压测调整。
- 答题、加入房间、主持人命令等离散事件及时处理。
- 手机立即显示本地操作反馈，最终得分以服务端为准。
- 大屏主要接收队伍进度、前列排名和阶段，不接收全场每次点击。
- 输入包含房间、局次、序号等信息；服务端处理重复、过期、错误阶段和超限输入。
- 客户端时间与点击数量不可直接信任；限制有效频率和贡献上限。

### 生命周期

准备 → 入场 → 倒计时 → 运行 → 结算 → 结束。运行中可暂停与继续，也允许主持人明确中止。中止与正常完成分别记录。

每个阶段规定可接受的操作。计时以服务端为准，暂停时明确冻结剩余时长和计分。

### 机制接口职责

初始化配置、处理玩家输入、推进时间、生成状态快照、结束并输出结果。不同主题复用同一机制；换肤不改变计分逻辑。

### 公平规则

- 个人竞速使用固定时长内的有效贡献，平分时采用明确且提前展示的处理方式。
- 团队模式发布前选择总贡献或按人数归一化，默认优先平衡分队并锁定计分成员口径。
- 归一化时不能用不断波动的在线人数作分母；断线、迟到玩家的处理规则须提前确定。
- AI 不在运行中秘密调整某队倍率。任何加成须来自预先公布的规则。
- 重连恢复原玩家及队伍，避免重复加入产生重复成绩。

## 7. Game DSL 与发布

DSL 是可验证的活动说明书，首期使用版本化的 JSON 结构，通过服务端模型校验。

| 配置部分 | 包含内容 |
| --- | --- |
| 基础 | 协议版本、活动标题、语言、时长 |
| 机制 | 竞速/拔河、个人/团队、输入类型 |
| 阵营 | 名称、颜色、分配方式 |
| 计分 | 有效输入上限、汇总方法、平分规则 |
| 阶段 | 入场、倒计时、运行、结果 |
| 品牌 | Logo 资源、主色、产品图、主题资源 |
| 文案 | 规则说明、主持词、欢迎语、结局 |
| 资源清单 | 资源标识、版本、用途 |

### 生成流水线

需求解析 → 模板选择 → 生成草稿配置 → 文案与资源生成 → 结构校验 → 语义校验 → 模拟试跑 → 可预览。

结构校验检查字段与类型；语义校验检查机制是否支持参数；试跑检查阶段可结束、结果合理及资源完整。

用户上传的 Logo 和产品图保留原样，品牌事实来自用户资料。文字使用页面文字层渲染，避免依赖图片生成中文字。

发布创建不可变配置版本并绑定完整资源清单。运行房间固定使用该版本。草稿修改不会影响正在运行的活动。

## 8. 数据与恢复

计划核心实体：组织、管理员、活动、活动版本、品牌资源、房间、游戏局次、玩家、房间成员、阵营、成绩、生成任务、主持人操作记录。

- 高频运行状态存房间实例内存。
- Redis 保存会话、归属和周期快照。
- PostgreSQL 保存正式配置和最终成绩。
- 结算使用局次唯一标识防止重复写入。
- 生成任务有状态、超时、有限重试和错误信息；重复执行不能产生多份正式结果。
- 客户端断线后重新认证并获取完整快照，再恢复后续更新。
- 只有周期快照不能保证零输入丢失。首期服务进程崩溃时允许明确中止并重开，不能伪装为无损恢复。
- 若后续要求严格续局，增加可重放输入记录、快照版本和房间所有权防重机制。

## 9. AI 导演的迭代边界

首期使用确定性的阶段推进、计时提示和主持人控制。第二阶段可让 AI 根据参与指标，从已注册的事件中推荐主持词或视觉事件。

允许的动作应有明确类型、触发条件、次数和时长限制；执行前校验，主持人可接管。AI 不参与高频计分，不直接改写规则，不延长已约定的比赛时长。

## 10. 开发阶段与验收

### P0：规则与交互定稿

- 明确竞速与拔河的计分、队伍人数、平分、迟到、断线和暂停规则。
- 确定管理端、玩家端、大屏端及主持人页面流程。
- 确定 DSL、事件协议和资源规范。
- 验收：一份无歧义的规则说明和可逐步演示的页面流程。

### P1：固定主题跑通

- 完成 Python 后端、微信登录入场、单房间与固定赛马主题。
- 跑通点击、进度同步、开始/暂停/结束和正式结算。
- 验收：至少 10 台真实手机完整参与一局，断线重连保留身份和成绩。

### P2：配置与玩法复用

- 抽出竞速配置，加入团队模式与拔河。
- 增加品牌上传、主题资源、草稿和发布版本。
- 验收：同一引擎加载两套明显不同的主题，无需修改代码；发布版本互不影响。

### P3：AI 生成与编辑

- 接入模型服务、异步生成、校验、试跑与进度展示。
- 支持自然语言修改主题、文案、队伍及允许的规则参数。
- 验收：未参与开发的用户输入真实需求后，能独立生成、预览、修改和发布。
- 记录生成总耗时、首个可玩预览耗时、失败率与单场生成成本。

### P4：活动闭环与现场稳定性

- 完成简洁签到上墙、品牌成绩卡、报告、资源预加载和异常提示。
- 模拟 100、300、500 连接逐级压测；模拟连接不能替代真实网络测试。
- 覆盖反复重连、重复输入、突然断网、超限输入、重复结算及 AI 服务失败。
- 验收：目标规模下完成真实活动，成绩一致，无持续消息积压；记录延迟与资源占用。

### P5：实地试点

- 邀请活动负责人独立搭建并主持一场小型活动。
- 记录搭建耗时、规则解释耗时、入场成功率、参与率和现场异常。
- 根据观察决定下一步优先增加主题、抽奖、答题还是 AI 导演。

阶段按验收结果推进。工期在 P0 后结合人员投入、素材来源和微信发布条件估算。

## 11. 质量指标与测试重点

建议首期以 300 人单场为目标负载，500 人为探索压测，不作为未经验证的容量承诺。

- 记录输入到权威状态广播的 P50/P95 延迟、队列长度、CPU、内存和断线率。
- 在明确测试网络条件下，可先以 P95 低于 300ms 作为调优目标，最终根据实测修订。
- 验证计分、平分、人数归一化、阶段迁移、暂停、去重和结算幂等。
- 验证玩家不能以主持人身份控制房间，也不能跨房间提交输入。
- 验证资源加载失败时能阻止开局并说明原因。
- 生成服务失败、战报生成失败与现场游戏运行相互隔离。
- 记录房间、局次、生成任务标识用于排查；不记录微信密钥或完整会话凭证。
